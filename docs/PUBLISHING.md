# Publishing instruction packages and workflows

Read [CONTRIBUTING](../CONTRIBUTING.md), [taxonomy](ROLE_TAXONOMY.md), [workspace adapters](WORKSPACE_ADAPTERS.md) and the current [registry](../registry.json). Inspect current main, active PRs, source ownership, and the approved target capability report before writing.

**Generation entrypoint:** Use the [Meta-LLM Orchestrator](../orchestrators/meta/meta-llm-orchestrator/README.md) and [generation architecture](AGENT_INSTRUCTION_GENERATION.md) for creating, upgrading, repairing and adapting specialist instructions. Do not author a specialist by copying another released ZIP. Existing specialists remain valid and directly usable when unchanged.

0. Before authoring, record the registry-first decision (`REUSE_UNCHANGED`, `UPGRADE`, `CREATE_NEW`, or `BLOCKED`) and the intended generated-agent environment. If unknown, ask one focused destination question; don't re-ask an answered question. Capture source-loading mode, registry write intent and verified target capabilities independently. `ADAPT_EXISTING` does not itself create a new canonical version.
1. Select kind: `conversation-orchestrator`, `primary-orchestrator`, `workflow-orchestrator`, `meta-orchestrator` or `specialist`; select one professional role, stable ID, version, capabilities, domains, aliases and intended use cases.
2. Resolve existing equivalents by registry search; prefer reuse or a new version over duplicating a capability. Differentiate the target runtime from the authoring workspace and probe actual tool permissions.
3. Publish one canonical package under `orchestrators/conversation/<id>/`, `orchestrators/primary/<id>/`, `orchestrators/workflow/<id>/`, `orchestrators/meta/<id>/` or `specialists/<domain>/<id>/`. **Lookup-first source contract:** `sources/SKILL.md`, `sources/manifest.json` with addressable `sections/`, `sources/README.md`, relevant `adapters/` and actual tools. Keep package-specific always-rules in the entrypoint and conditional guidance in manifest-indexed sections. **Legacy packages** retain their compiled instructions and `99_manifest.json` until explicitly migrated; do not silently rewrite the other packages.
4. Create a real binary `<id>_vN.zip` with exactly one `<id>/` root and byte-identical browsable source files. Validate ZIP CRC, source inventory, section IDs, read_when/requires closure, word counts, SHA-256, and generated entrypoint lookup tables. A README link is not an archive; do not register pending source-only entries as available.
5. Preserve previous versioned ZIPs and Git blobs. Pure directory moves should reuse blob SHA where possible; instruction changes create a new version. Disclose reconstruction provenance if original bytes are unavailable. Compiled prompt-only or upload-limited outputs are **generated dist artifacts**, never hand-maintained canonical duplicates.
6. Update `registry.json` (schema v3), category/root READMEs, workflow references, ownership matrices, migration ledger and search tests in the same PR, but only for actual paths. New modules must appear in the manifest source inventory; stale links block publication.
7. Run registry validation and the relevant archive/workflow/ownership tests. Test real runtime capabilities or installation only when the target tools actually exist; unsupported or unrun provider/subagent tests are **NOT_RUN**, not passing.
8. Migrate existing specialists only in separately scoped reviewed change(s) with old-to-new rule traceability, preserved historical ZIPs, independent schema/behavior tests, and human approval. Documentation-only foundation changes must not modify legacy specialist packages.
9. Open/update one reviewable PR with source count, ZIP paths, version evidence, generated adapter limitations, and verification results. Do not claim deployment, merge or human approval without actual tool confirmation.

Published packages define behavior; they do not prove a running workflow engine or a hosted agent gateway. The shared rules file is still draft v0 and the approval policies require separate reconciliation. Never run the legacy one-time `scripts/rebuild_registry.py` against the current layout.
