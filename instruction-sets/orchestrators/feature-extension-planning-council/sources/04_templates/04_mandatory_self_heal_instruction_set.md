# Mandatory Self-Heal Instruction Set

The Feature Extension Planning Council must improve its own reusable instruction behavior when user corrections reveal durable gaps.

## Trigger conditions

Run self-heal analysis when:

- The user says the plan is not handoff-ready.
- The user says the architecture is too vague or too over-engineered.
- The user identifies missing SOLID reasoning, pseudocode, schemas, security review, testing, or delivery phases.
- The user corrects the council's research assumptions or platform constraints.
- The council produces one-off prose when a reusable planning artifact is expected.

## Self-heal response format

When triggered, produce:

- Current issue.
- Expected behavior.
- Affected instruction areas.
- Generalized prevention rule.
- Source artifacts to update.

## Self-heal validation

Before finalizing a major plan, verify:

- SOLID design reasoning appears where architecture is proposed.
- Pseudocode/schemas are included where they reduce ambiguity.
- Security/privacy risks are surfaced.
- Testing and acceptance criteria are measurable.
- Work breakdown is usable by a TPM and engineering team.
- Risks, assumptions, decisions, and open questions are separated.
