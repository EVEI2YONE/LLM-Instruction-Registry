# Generate and adapt

Proceed only after recorded registry decision **and resolved user-intended execution environment**. Portable orchestrator source does not imply platform-neutral generated output. If the target is unknown, return the single destination clarification question instead of writing agent instructions. Never infer that the new agent will run in the environment where this generator currently executes.

1. Classify instructions by authority and trigger: global approved governance; package-specific Always rules; conditional procedures; templates; machine-validated contracts; runtime adapters; volatile pinned external knowledge.
2. Preserve one canonical tree. Use a concise entrypoint, manifest-indexed sections with stable IDs, observable `read_when`, explicit `requires`, real paths, and source inventory. Never invent successful lookup or host-specific APIs.
3. Tailor content, tool permissions, file layout, loading behavior, install steps, and limitations to the user's resolved environment. Derive runtime delivery from the same canonical bytes:
   - prompt-only: assemble all required normative instructions into a bounded self-contained payload and report omissions;
   - readable files: provide manifest-guided manual loading;
   - verified tool runner: expose exact invocation/permission contracts;
   - child-agent runner: use scoped task envelopes, bounded budgets, audited artifact ownership, and explicit fan-in.
4. Keep local or hosted SDK details in optional adapters, not core behavior. Do not create multiple separately maintained source versions.
5. Preserve provenance and any legacy behavior migration map. Record omissions, changes in meaning, and conflicting approval authorities for human review.
6. Limit actions to explicit permissions. Generation alone never starts an agent, registers an integration, installs a package, or publishes a release.

When authority/source access is missing, a labeled review candidate is permissible but release-ready claims are not.
